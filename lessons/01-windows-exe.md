## 【为什么要学】

你后面要做的所有事——找游戏里的资源数值、理解为什么地址每次重启都变、写一个能读取别的进程内存的小程序——都建立在同一个前提上：

> **修改器不是"魔法"，它只是"知道数据在虚拟地址空间的哪个位置，然后通过系统提供的合法接口去读写那块内存"。**

所以第一步必须搞清楚：一个 EXE 是怎么从"磁盘上的一堆字节"变成"内存里一个活着的进程"的。
搞不清这一步，你后面看到的每一个地址都会像玄学。

## 【核心概念】

### 1. 编译器生成了什么

```
lab01.c  ──编译(compile)──►  一堆机器指令 + 数据（目标文件 .obj）
         ──链接(link)─────►  lab01.exe（一个 PE 文件）
```

- **编译**：把你的 C 语句翻译成 CPU 能直接执行的**机器指令**（也就是汇编的二进制形式）。
  `int money = 100;` 会变成一条类似 `mov dword ptr [rbp-4], 64h` 的指令。
  注意：`64h` 就是十六进制的 100。**"100" 变成了指令的一部分，而不是一个"存放着 100 的格子"。** 这个区别今天你会亲眼看到。
- **链接**：把"你的代码"和"别人写好的代码"（C 运行库、Windows API）拼成一个完整文件，
  并把所有函数的地址/名字对齐。你在源码里写的 `printf`，编译器并不知道它的代码在哪，
  链接器只是在 EXE 里记一笔："我需要一个叫 `printf` 的函数，加载时帮我找到它"——这就叫**导入(Import)**。

### 2. EXE 文件是什么：PE 格式

Windows 上的 `.exe` 和 `.dll` 是同一种文件格式，叫 **PE（Portable Executable）**。
你可以把它理解成"一份带说明书的搬家清单"：

```
偏移 0x00  ┌──────────────────────────────┐
           │ DOS 头  "MZ"                 │  历史遗留，主要作用是告诉你 PE 头在哪
           ├──────────────────────────────┤
           │ PE 签名 "PE\0\0"             │
           ├──────────────────────────────┤
           │ COFF 文件头                  │  32位还是64位？有几个节？
           ├──────────────────────────────┤
           │ 可选头 Optional Header       │  ★ 最重要的部分：
           │   AddressOfEntryPoint        │     CPU 从哪开始跑
           │   ImageBase                  │     希望被加载到哪个基址
           │   SizeOfImage                │     加载后占多大地址范围
           │   DllCharacteristics         │     是否支持 ASLR / DEP
           │   导入表/资源表 的位置        │
           ├──────────────────────────────┤
           │ 节表 Section Table           │  ★ 每一行描述一块数据：
           │   .text  代码                │     在文件里的偏移 + 在内存里的 RVA + 大小 + 权限
           │   .rdata 只读数据/字符串      │
           │   .data  已初始化的全局变量    │
           │   .bss/  未初始化的全局变量    │     （文件里不占空间，只记一个大小）
           │   .reloc 重定位信息           │     ← ASLR 能实现全靠它
           ├──────────────────────────────┤
           │ 各节的实际字节                │
           └──────────────────────────────┘
```

**两个坐标系一定要分清**（第 2、7 课会反复用到）：

| 名字 | 含义 | 例子 |
|---|---|---|
| **文件偏移 (Raw Offset)** | 在磁盘上这个 `.exe` 文件里的第几个字节 | `0x1144` |
| **RVA (Relative Virtual Address)** | 加载进内存后，距离**模块基址**多少字节 | `0x1040` |
| **VA (Virtual Address)** | 内存里的真实地址 = 基址 + RVA | `0x7FF6A1B21040` |

同一个变量，在文件里和在内存里的坐标是不一样的。新手最容易在这里绕晕。

### 3. 双击 EXE 之后，Windows 做了什么

```
你双击 lab01.exe
   │
   ▼
explorer.exe（桌面）调用 ShellExecute → 最终走到内核的 CreateProcess
   │
   ▼  ★ 内核做的事：
   ├─ 1. 创建一个"进程对象"（EPROCESS），分配一个 PID
   ├─ 2. 给这个进程开辟一块全新的、空的【虚拟地址空间】
   │      （64 位 Windows 上是 128TB 的用户可用地址范围，此刻几乎全是空的）
   ├─ 3. 在进程里创建【第一个线程】（主线程），给它一套寄存器和一个【栈】
   │
   ▼  ★ ntdll.dll 里的加载器 (LdrpInitializeProcess) 做的事：
   ├─ 4. 打开 EXE 文件，读 PE 头，按节表把各个节【映射】进虚拟地址空间
   │      .text → 标记为"可读可执行、不可写"
   │      .data → 标记为"可读可写、不可执行"
   │      这一步叫 "映像加载 (image mapping)"，不是把文件拷贝进去，
   │      而是让内存页和文件内容建立映射关系（用到时才真正读盘，这叫按需分页）
   ├─ 5. 处理【导入表】：递归加载 kernel32.dll、ucrtbase.dll…… 并把
   │      你调用的每个 API 的真实地址填进 IAT（导入地址表）
   ├─ 6. 处理【重定位表 .reloc】：如果实际加载基址 ≠ ImageBase（ASLR 生效时），
   │      就把文件里所有写死的地址加上差值修正一遍
   │
   ▼
   └─ 7. 让主线程的 RIP（指令指针）指向 AddressOfEntryPoint，CPU 开始执行
          ↓
          入口点不是你的 main！它是 C 运行库的启动代码，负责：
          初始化 CRT / 堆 / 命令行参数 / 全局构造函数
          ↓
          然后它才【调用】你的 main()
          ↓
          main 返回 → 启动代码调用 ExitProcess → 内核销毁进程
```

**关键结论**：你的 `main` 是被别人调用的一个普通函数。EXE 里真正的"起点"是入口点。
这一点你在实验 B 里能直接看到（`AddressOfEntryPoint` 的地址往往不等于 `main` 的地址）。

### 4. 进程 vs 线程

| | 进程 (Process) | 线程 (Thread) |
|---|---|---|
| 是什么 | **资源**的容器：一份虚拟地址空间 + 句柄表 + PID | **执行**的单位：一套寄存器 + 一个栈 + 一个执行位置(RIP) |
| 拥有什么 | 内存、文件句柄、DLL 列表 | CPU 时间、栈空间、寄存器状态 |
| 数量关系 | 1 个进程 | 至少 1 个线程，可以有很多个 |
| 隔离性 | 进程之间内存互相看不见（除非用系统提供的接口） | 同进程的线程共享同一份地址空间 |
| 类比 | 一栋房子（有地址、有家具） | 房子里走动的人（真正在干活） |

这就是为什么"修改器要读游戏内存"必须先 `OpenProcess` 拿到句柄——
因为 Windows 默认**不允许**一个进程碰另一个进程的内存。这个隔离是操作系统给的，不是游戏给的。
（第 10 课我们会正面处理这件事。）

### 5. 代码在哪、变量在哪

一个进程加载完之后的地址空间，粗略长这样（64 位，从低到高）：

```
高地址  ┌─────────────────────┐  0x7FFF...
        │ 内核空间（用户态看不见）│
        ├─────────────────────┤
        │ 栈 Stack ↓ 向下生长   │  ← 局部变量 money 住这里
        │        ...           │
        │ 堆 Heap  ↑ 向上生长   │  ← malloc/new 出来的东西
        ├─────────────────────┤
        │ 各种 DLL             │  ← kernel32.dll、ucrtbase.dll、游戏的引擎 DLL
        ├─────────────────────┤
        │ EXE 映像             │  ← ImageBase 开始
        │   .text  代码        │  ← 你的 main 的机器指令
        │   .rdata 常量/字符串  │
        │   .data  全局变量     │  ← int g_money = 200; 住这里
        │   .bss   未初始化全局 │
低地址  └─────────────────────┘  0x0000...（最低的 64KB 故意留空，
                                    这样"用了空指针"会立刻崩，而不是悄悄出错）
```

三种变量的命运完全不同：

| 变量 | 住哪 | 谁分配 | 活多久 | 值存在 EXE 里吗 |
|---|---|---|---|---|
| `int g = 200;`（全局） | `.data` 段 | 链接器/加载器 | 整个进程生命周期 | **存在**（文件里就有 4 个字节 `C8 00 00 00`） |
| `int g2;`（全局未初始化） | `.bss` 段 | 加载器（清零） | 整个进程生命周期 | **不存在**（文件里只记一个"要 N 字节"的大小） |
| `int money = 100;`（局部） | 主线程的**栈** | `main` 里的 `sub rsp, N` 指令 | 从 `main` 被调用到 `main` 返回 | **不存在**（文件里只有"把 100 搬进去"这条指令） |
| `malloc(4)`（堆） | 堆 | 运行时向系统申请 | 从 `malloc` 到 `free` | **不存在**（连地址都是运行时才知道） |

这张表就是第 6、7 课的全部伏笔：
**游戏里的资源、血量、单位数量，绝大多数属于最后一行——运行时才在堆上造出来的对象。**
所以它们的地址每次启动都不同，所以你需要"指针链"。

### 6. 为什么退出后 money 就不存在了

两层原因，别混：

1. **逻辑层**：`money` 是 `main` 的栈帧里的一个格子。`main` 一返回，栈指针 `rsp` 往上抬，
   这个格子就被"退还"了，下一次函数调用会直接覆盖它。此时即使进程还活着，`money` 也已经死了。
2. **系统层**：进程退出时，内核把整个虚拟地址空间的所有页面全部解除映射并回收，
   PID 作废，句柄失效。别人再想读这块内存，`OpenProcess` / `ReadProcessMemory` 会直接失败。

有意思的细节：**物理内存不一定被立刻清零**。页面被回收后，里面的旧字节可能还在物理内存里躺一会儿，
直到被分配给别人。这就是"未初始化局部变量有时会看到奇怪的旧值"的原因，也是很多安全漏洞的根源。
但对你的程序来说，那个地址已经**不再属于你**了——这才是"不存在"的真正含义。

## 【我应该看到什么】

### A4：反汇编里的 `main`（MinGW -O0，x64，真实输出）

```asm
main:
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16                        ; ← 在栈上"腾出 16 字节"，局部变量就住这里
    mov     DWORD PTR -4[rbp], 100         ; ★★★ money = 100 就是这一条
    mov     DWORD PTR -8[rbp], 1           ;     alive = 1
    mov     eax, DWORD PTR -4[rbp]         ;     读取 money 准备传给 printf
    ...
    call    printf
.L2:
    mov     eax, DWORD PTR -8[rbp]         ; ┐
    test    eax, eax                       ; │ while(alive) 循环体：
    jne     .L2                            ; ┘ 每次重新读内存，所以删不掉
```

**这一条 `mov DWORD PTR -4[rbp], 100` 回答了你今天最重要的问题：**

- `money` 没有一个"属于自己的固定地址"。它的地址是 `rbp - 4`，**运行时**才由 `rbp` 决定。
- `100` 是这条指令的**立即数**，也就是指令自身的一部分，不是"某个格子里的内容"。
- 所以：**变量 = 地址 + 那个地址上的值**；而赋值 = 一条把值搬进那个地址的指令。

（MSVC 的写法会略有不同，可能是 `mov dword ptr [money], 64h` 并带上 `/RTC` 检查代码，本质一样。）

### A5：Release 版的行为变了（真实输出对比）

**你原本给我的那一版**（`int money = 100; while(1){}`，没有 `printf`、没有 `volatile`），
`-O2` 编译出来 `main` 只剩这样：

```asm
main:
    sub  rsp, 8
    lea  rdi, .LC0[rip]
    call puts@PLT
.L2:
    jmp  .L2          ; ← while(1) 变成一条"自己跳自己"的 jmp
```

`money` **整个消失了**——编译器发现它被赋值后从来没人读过，于是把这条赋值连同那 4 字节栈空间一起删掉。
如果你连 `printf` 都没有，`main` 会缩成 `jmp .L2` 三四个字节，进程照样卡住但没有任何输出，
窗口看起来就是"一闪而过 / 什么都没有"。

**我给你的 `lab01.c`（带 `volatile int alive`）**，`-O2` 编译出来是这样：

```asm
main:
    sub  rsp, 24
    mov  esi, 100                    ; ★ money 被优化没了，100 直接当成 printf 的参数放寄存器里
    lea  rdi, .LC0[rip]
    xor  eax, eax
    mov  DWORD PTR 12[rsp], 1        ;   alive = 1（volatile，必须真的写进内存）
    call printf
.L2:
    mov  eax, DWORD PTR 12[rsp]      ; ┐ volatile：每次循环都必须重新从内存读一遍，
    test eax, eax                    ; │ 所以这个循环删不掉
    jne  .L2                         ; ┘
```

两个现象合起来就是今天的重点：

1. **`money` 在 Release 里不再是一个"内存中的格子"**，它被编译器变成了一个常量、一个寄存器值。
   它没有地址，你也搜不到它。
2. **`volatile` 是唯一能强迫编译器"老老实实把它放在内存里、每次都去读"的手段。**

> `volatile` 的意思是"这块内存随时可能被程序之外的东西改动，不许你假设它的值"。
> 讽刺的是——**修改器恰恰就是那个"程序之外的东西"**。
> 所以正式发布的商业程序（包括游戏）几乎总是开着优化的，
> 你想找的那个变量在 Release 版里很可能压根不以"一个独立格子"的形式存在。
> 这句话先埋着，第 6 课你会在游戏上撞到它，第 10 课回收。

### B：`pe_view.py` 的输出要点

你应该看到类似（数字随编译器版本不同，结构一定相同）：

```
Machine            : 0x8664  AMD64 (64 位 / x64)
AddressOfEntryPoint: 0x1234     ← 不是 main 的地址
ImageBase          : 0x140000000 ← 64 位 EXE 的经典默认基址（32 位是 0x400000）
DllCharacteristics :
    [x] 0x0040  DYNAMIC_BASE  -> ASLR：每次启动基址可以不同
    [x] 0x0100  NX_COMPAT     -> DEP：数据页默认不可执行
节表：
    .text     VirtAddr 0x00001000   RawOffset 0x00000400   CODE 代码,可执行
    .rdata    VirtAddr 0x00002000   RawOffset 0x00000600
    .data     VirtAddr 0x00003000   RawOffset 0x00000800   IDATA 已初始化数据
    .reloc    ...
导入的 DLL：
    - KERNEL32.dll
    - api-ms-win-crt-*.dll  或  msvcrt.dll / ucrtbase.dll
```

**三个必须记住的点：**

1. `.text` 的 RVA 和 RawOffset **不相等**——这就是"文件坐标 ≠ 内存坐标"的实证。
2. 你的源码只有 20 行，却导入了 `KERNEL32.dll` 和一堆 CRT 的 DLL。
   `printf` 的代码**不在你的 EXE 里**，它是运行时才被加载进来、地址才被填好的。
3. 有 `.reloc` 节 + `DYNAMIC_BASE` 标志 → 这个 EXE **支持 ASLR**。
   第 7 课讲"为什么地址每次都变"时，罪魁祸首就是它。（《英雄连》是 2006 年的老游戏，
   它的主 EXE **不一定**开了 ASLR——这件事你要自己用 `pe_view.py` 去查，别猜。）

### C：搜 "100" 的结果

- `lab01_debug_x86.exe` 搜 `100`：**可能 0 个匹配，也可能 1~2 个**。
  0 个是因为编译器可能用别的指令写法；1 个的话，那个匹配点周围的字节会长这样：
  `... C7 45 FC 64 00 00 00 ...` ← `C7 45 FC` 是操作码，`64 00 00 00` 才是 100。
  **它躲在指令中间，不是一个独立的"数据"。**
- `lab01b_debug_x86.exe` 搜 `200`（全局变量）：**能搜到**，而且匹配点周围很干净，
  前后都是别的常量——因为它就躺在 `.data` 段里，是文件的一部分。
- 搜 `300`（malloc 后写入堆的值）：**只能搜到 `mov ..., 12Ch` 那条指令**（0x12C = 300），
  因为堆上的那块内存运行时才存在。

> 一句话总结实验 C：**全局变量的"值"存在文件里；局部变量和堆数据的"值"只在运行时存在。**
> 第 6 课你在游戏内存里搜资源数量，搜的就是"运行时才存在"的那一类——
> 所以你不可能靠翻 EXE 文件找到它，必须去搜**活着的进程的内存**。

### D：任务管理器

- 能看到 `lab01_debug_x86.exe`，PID 是一个 4~5 位数。
- **线程数 = 1**（只有主线程；如果显示 2~3，是 CRT/系统帮忙建的辅助线程，正常）。
- **提交大小** 通常在几百 KB ~ 2 MB，比 EXE 文件大小（几十 KB）大得多。
  因为进程一启动就加载了 kernel32、ntdll、CRT 等一堆 DLL，还要预留栈（默认 1MB）。
- 两个实例的 **PID 不同**，但打印出来的 **`&money` 地址很可能完全相同**。
  ★ 这是今天第二个"啊哈时刻"：地址相同却互不干扰，因为**每个进程有自己独立的一套虚拟地址空间**，
  同一个数字 `0x61FEFC` 在进程 A 和进程 B 里指向的是两块完全不同的物理内存。

### E：三种地址的数量级（典型 x64 结果）

```
代码 main    : 0x00007FF6A2B415A0   ← 在 ImageBase 附近（EXE 映像）
全局 g_money : 0x00007FF6A2B44020   ← 也在 EXE 映像里，比代码地址高一点点（.data 在 .text 之后）
局部 m_money : 0x00000061F3EFF8C0   ← 明显低一截，这是栈
堆   h_money : 0x000001E5A7C90040   ← 又是另一个区间，这是堆
```

你的具体数字会不一样，**但相对关系应该一致**：代码和全局挨在一起，栈和堆各自在别处。
如果开了 ASLR，你重启程序后 `main` 的地址会变——先记住这个现象，第 7 课解释。
