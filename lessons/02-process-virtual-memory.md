## 【核心概念】

### 1. 虚拟地址空间：每个进程一份的"假内存"

物理内存（你插的那 16GB 条）只有一份，但每个进程都以为自己独享一整条连续的地址。
这个"以为"是 CPU 的 MMU（内存管理单元）+ 操作系统联手造出来的假象：

```
      进程 A 眼中的地址            物理内存            进程 B 眼中的地址
   ┌──────────────┐                              ┌──────────────┐
   │ 0x00401000   │──────┐          ┌──────────┐ │ 0x00401000   │
   │ (它的代码)    │      └────────►│ 物理页 1 │ │ (它的代码)    │
   ├──────────────┤                 ├──────────┤ ├──────────────┤
   │ 0x00402000   │──────┐          │ 物理页 2 │◄─┘ 0x00402000   │
   │ (它的全局变量) │      └────────►│          │   │ (它的全局变量) │
   └──────────────┘                 └──────────┘ └──────────────┘
```

**同一个数字地址，在不同进程里指向不同的物理页。**
这就是第 1 课实验 D 那个悬念的答案：两个 `lab01_debug_x86.exe` 打印出相同的 `&money`，
却互不干扰——因为那个地址在两个进程里根本不是同一块物理内存。

三个直接后果，你以后会天天遇到：

| 后果 | 对逆向的意义 |
|---|---|
| 地址是**进程私有**的 | 想读游戏内存，必须"进入那个进程的视角"，也就是拿到它的句柄 |
| 地址空间是**连续**的假象 | 你可以从 0 开始一段一段扫完整个空间（Cheat Engine 就是这么干的） |
| 大部分地址是**空的** | 扫描时可以直接跳过 Free 区域，速度提升几百倍 |

32 位进程的地址空间：`0x00000000 ~ 0xFFFFFFFF`，共 4GB。
其中**用户态只能看到低 2GB**（`0x00000000 ~ 0x7FFFFFFF`），高 2GB 是内核的。
《英雄连》是 32 位程序，所以它的全部家当——EXE、几十个 DLL、堆、栈——都必须挤在这 2GB 里。
（有个 `/LARGEADDRESSAWARE` 开关能扩到 4GB，第 1 课 `pe_view.py` 输出里那个
`LARGE_ADDRESS_AWARE` 标志说的就是它。你可以顺手查一下游戏 EXE 有没有开。）

### 2. 页，和每一块区域的三个属性

系统不按"字节"管内存，按**页**管。x86/x64 上一页 = **4096 字节（4KB）**。
所有地址的分配、保护、换出，都是以页为单位做的。

你用 `VirtualQueryEx`（或者 System Informer 的 Memory 页）问系统"这块地址是什么情况"，
它会告诉你三件事：

**① State 状态——这块地址现在算什么**

| 值 | 名字 | 含义 | 能读吗 |
|---|---|---|---|
| `0x10000` | **MEM_FREE** | 空闲，谁都没占 | 不能 |
| `0x2000` | **MEM_RESERVE** | 地址范围被占住了，但还没配物理存储 | 不能 |
| `0x1000` | **MEM_COMMIT** | 已提交，系统保证你写就有地方放 | **能** |

> **Reserve vs Commit 是新手最容易糊的一对。**
> 打个比方：Reserve 是"我在地图上圈了一块地"，Commit 是"这块地已经通了水电可以盖房"。
> 32 位进程创建线程时，默认会 **Reserve 1MB 栈空间但只 Commit 几 KB**——
> 所以你在 System Informer 里会看到一块 1MB 的 Reserve，紧挨着一小块 4KB~64KB 的 Commit。
> 线程真的用了很多栈，Commit 的部分才会一点点长大。
> 任务管理器里的"提交大小"统计的就是 Commit，不是 Reserve。

**② Type 类型——这块内存是谁造出来的**

| 值 | 名字 | 来源 |
|---|---|---|
| `0x1000000` | **MEM_IMAGE** | 被加载器映射进来的 **EXE / DLL**。★ 找模块就看它 |
| `0x40000` | **MEM_MAPPED** | 被映射进来的**数据文件**、共享内存、字体、图标 |
| `0x20000` | **MEM_PRIVATE** | 进程私有的。**堆、栈、`VirtualAlloc` 出来的都算它** ★ 找游戏数据就看它 |

**③ Protect 保护——这块内存允许干什么**

| 显示 | 常量 | 典型用途 |
|---|---|---|
| `R-X` / `PAGE_EXECUTE_READ` | `0x20` | **代码段**。可读可执行，**不可写** |
| `RW-` / `PAGE_READWRITE` | `0x04` | **全局变量、堆、栈**。可读可写，**不可执行** |
| `R--` / `PAGE_READONLY` | `0x02` | 字符串常量、只读数据、DLL 的导入表 |
| `RWX` / `PAGE_EXECUTE_READWRITE` | `0x40` | 可写又可执行。**正常程序很少有**，JIT / 加壳 / 自修改代码 / 注入代码才会出现 |
| `---+G` / `PAGE_GUARD` | `0x100` | **哨兵页**。栈的边界，线程栈用超了碰到它就报栈溢出 |

> 这三张表你不用背。但请记住一个组合技：
> **"游戏的可变状态"一定在 `Private` + `Commit` + `RW-` 的区域里。**
> 第 6 课做内存扫描时，先把范围限制在这类区域，假阳性会少一大半。
> （Cheat Engine 里那个 "Memory Regions" / 只扫 Writable 的选项，底层就是这个道理。）

### 3. 一个真实进程的地址空间全景

这是 32 位进程从低到高的典型布局（**地址是示意，你的会不同**）：

```
0x7FFF0000 ┌────────────────────────────────────────┐ ← 32 位用户态上限 (2GB)
           │ 0x7FFE0000  SharedUserData             │  Mapped, R--
           │            每个进程都有的共享只读页，      │  （系统把时钟、版本号放这里）
           │            地址永远一样，内容也一样        │
           ├────────────────────────────────────────┤
           │ 0x77xxxxxx  ntdll.dll                  │  Image
           │ 0x76xxxxxx  kernel32.dll               │  Image
           │ 0x75xxxxxx  kernelbase / ucrtbase ...  │  Image
           │ 0x74xxxxxx  各种系统 DLL                │  Image
           │             ← 每个 DLL 内部还会按保护属性   │
           │               拆成好几个区域：             │
           │               .text  R-X / .rdata R-- /  │
           │               .data  RW-                 │
           ├────────────────────────────────────────┤
           │ 0x12340000  lab02a 用 VirtualAlloc      │  Private, Commit, RW-
           │             "点名"要的那块               │
           ├────────────────────────────────────────┤
           │ 0x05xxxxxx  堆（大块 malloc）            │  Private, Commit, RW-
           │ 0x01xxxxxx  默认进程堆                   │  Private, Commit, RW-
           │             中间夹着一些 Reserve 区        │  Private, Reserve
           ├────────────────────────────────────────┤
           │ 0x00Bxxxxx  线程 3 的栈                  │  Private, Commit, RW-
           │ 0x00Axxxxx  线程 2 的栈                  │  Private, Commit, RW-
           │ 0x009xxxxx  线程 1 的栈                  │  Private, Commit, RW-
           │ 0x0019xxxx  主线程的栈 ← money 住这里     │  Private, Commit, RW-
           │             每块栈下面都跟着一大段 Reserve  │  Private, Reserve (1MB)
           │             和一页 GUARD                  │  Private, Commit, ---+G
           ├────────────────────────────────────────┤
           │ 0x00F5xxxx  你的 EXE 映像                │  Image
           │             0x00F51000 .text   R-X      │  ← main 的机器指令
           │             0x00F54000 .rdata  R--      │  ← "money = %d" 这些字符串
           │             0x00F56000 .data   RW-      │  ← g_money = 200
           ├────────────────────────────────────────┤
           │ 0x00010000  TEB（线程环境块）             │  Private, RW-
0x00000000 ├────────────────────────────────────────┤
           │ 0x00000000 ~ 0x0000FFFF  永远不分配       │  Free
           └────────────────────────────────────────┘ ← 故意留空的 64KB，
                                                          用空指针会立刻崩
```

**★ 本课最容易被忽略、但最重要的一个观察：**

> 第 1 课你在 `pe_view.py` 里看到 EXE 有 4~6 个**节**（.text/.rdata/.data/.reloc）。
> 但在活着的进程里，它们**不是一个区域，而是被拆成了好几个区域**——
> 因为系统是按"保护属性相同"来划分内存区域的，
> `.text` 是 R-X、`.rdata` 是 R--、`.data` 是 RW-，三种保护，所以拆成三块。
>
> 所以你在 System Informer 的 Memory 页里会看到：**一个 DLL = 好几行连续的地址**。
> 它们的 Type 都是 `Image`，基址相同（都属于同一个模块），只是 Protect 不同。
> 而 Modules 页里那个 DLL 只显示**一行**，Size 是整个 `SizeOfImage`。
> 两个页面看的是同一个东西的两个视角。

### 4. DLL 是什么，怎么被加载

**DLL（Dynamic Link Library，动态链接库）本质上就是一个 PE 文件，和 EXE 是同一种格式。**
区别只有两点：

1. DLL 的 COFF 头里有 `IMAGE_FILE_DLL` 标志（`pe_view.py` 输出里那个 `0x2000 DLL` 就是它），
   它不能独立运行，没有自己的进程。
2. DLL 会**导出（Export）**一批函数和变量，供别人按名字调用。

> 你第 1 课跑的 `pe_view.py` 已经能识别这个标志了。
> 换句话说：**你已经有能力自己判断一个文件是 EXE 还是 DLL**，不用猜。

**两种加载方式：**

| | 隐式加载（静态链接到导入表） | 显式加载（动态） |
|---|---|---|
| 什么时候 | 进程启动时，加载器自动做 | 代码运行到那一行时才做 |
| 你怎么写 | `printf(...)` 就完了 | `LoadLibrary("xxx.dll")` → `GetProcAddress(h, "FuncName")` → 调用 → `FreeLibrary` |
| 在 EXE 里的痕迹 | 导入表里有一行 `xxx.dll` + 函数名 | **只有一个字符串** `"xxx.dll"`，导入表里看不到 |
| 如果 DLL 不存在 | **进程根本启动不了**，弹"缺少 xxx.dll" | `LoadLibrary` 返回 NULL，程序可以自己处理 |
| 谁在用 | 99% 的常规依赖 | 插件、可选功能、皮肤、DLC、**以及注入代码** |

第 1 课你的 EXE 导入了 `KERNEL32.dll` —— 那就是隐式加载。
第 11 课讲代码注入时用的就是显式加载：让目标进程自己去 `LoadLibrary` 你的 DLL。
现在只需要知道**这两件事是不同的机制**，注入不是"凭空出现的"。

**加载一个 DLL 时，系统做了什么？**

```
LoadLibrary("xxx.dll")  或  进程启动时处理导入表
   │
   ├─ 1. 按搜索顺序找到文件（应用目录 → 系统目录 → PATH ...）
   ├─ 2. 读它的 PE 头，拿到 ImageBase 和 SizeOfImage
   ├─ 3. 在地址空间里找一块够大的、没被占的地方，把各节映射进去
   │     如果首选 ImageBase 空着 → 就用它（所以系统 DLL 每次都在差不多的位置）
   │     如果被占了 / 开了 ASLR   → 换一个基址，然后按 .reloc 修正
   ├─ 4. 递归处理这个 DLL 自己的导入表（DLL 也依赖别的 DLL）
   ├─ 5. 调用它的 DllMain(DLL_PROCESS_ATTACH)
   └─ 6. 返回这个 DLL 的【基址】(HMODULE)
```

**第 6 步返回的那个基址，就是第 7 课"模块基址"的全部含义。**
你在 `lab02d.exe` 的输出里会看到一长串这样的基址，
以后看到别人写 `"游戏DLL名.dll"+0x1A2B3C`，那个引号里的部分就是在说这个基址。

**共享**：同一个 `kernel32.dll`，被 200 个进程加载，磁盘上只有一份文件，
物理内存里也基本只有一份——每个进程只是把它"映射"进自己的地址空间，指向同一批物理页。
代码段是只读的，大家可以共用；数据段是可写的，用到写的时候系统才给它复制一份私有副本（Copy-on-Write）。
这就是为什么你的 EXE 只有 30KB，进程却"占用"了几 MB——但其中大部分是和别人共享的。

### 5. Windows API 是什么

去掉神秘感，一句话：

> **Windows API 就是微软写好的、放在系统 DLL 里、通过"导出表"公开出来的一批函数。**

你调用 `VirtualQueryEx(...)` 时，发生的事情是：

```
你的代码：call VirtualQueryEx
   ↓ 这条 call 跳到的其实是你 EXE 里的 IAT（导入地址表）中的一个格子
   ↓ 那个格子里存着 kernel32.dll 中 VirtualQueryEx 的真实地址（加载时被填好的）
   ↓ 跳进 kernel32.dll 执行
   ↓ kernel32 只是个"包装层"，它再通过 syscall 陷入内核
   ↓ 内核里的 ntoskrnl.exe 真正去查这个进程的页表
   ↑ 结果原路返回
```

所以：

- **API 的实现代码不在你的 EXE 里**，在系统 DLL 里（第 1 课实验 B 你已经验证过）。
- **API 是有文档的公开接口**，用它读进程内存是**合法且被支持的操作**，不是"黑进"什么。
- 你的程序和游戏调用的是同一批 API。游戏没有任何特权——它也受同一套规则约束。

这一课你会用到 4 个 API，全部属于"观察类"，一个都不改任何东西：

| API | 干什么 | 出处 |
|---|---|---|
| `GetCurrentProcess()` | 拿到本进程的伪句柄 `(HANDLE)-1` | kernel32 |
| `OpenProcess(权限, 继承, PID)` | 用 PID 换一个**真句柄**，才能操作别的进程 | kernel32 |
| `VirtualQueryEx(句柄, 地址, &mbi, size)` | 问"这个地址所在区域的基址/大小/状态/类型/保护" | kernel32 |
| `ReadProcessMemory(句柄, 地址, 缓冲区, 大小, &实读)` | 把目标进程某地址的内容复制到我自己这儿 | kernel32 |

### 6. 调试器和内存工具是怎么"看到"一个进程的

**System Informer 的 Memory 页、Cheat Engine 的扫描、x64dbg 的内存地图、
以及你以后自己写的观察器——底层用的是同一个循环：**

```c
BYTE *addr = 0;
while (addr < 上限) {
    VirtualQueryEx(hProcess, addr, &mbi, sizeof(mbi));   // 问这一块的情况
    if (mbi.State == MEM_COMMIT && 我关心的类型/保护) {
        ReadProcessMemory(hProcess, mbi.BaseAddress, buf, mbi.RegionSize, &rd);  // 读出来
        在 buf 里找我想要的数值;
    }
    addr = mbi.BaseAddress + mbi.RegionSize;             // 跳到下一块
}
```

这就是 `lab02e.c` 的全部内容（我少写了 Read 那一步，因为这一课只看不读）。

**看懂这个循环，你就同时看懂了：**
- System Informer 的 Memory 页为什么能列出一张表
- Cheat Engine 第一次扫描为什么慢（它要把所有 Commit 区域全读一遍）、
  第二次扫描为什么快得多（只扫上次的候选地址）
- 你自己写的观察器需要哪些代码

### 7. PID 不是 HANDLE（这一条请务必记住）

| | PID | HANDLE |
|---|---|---|
| 是什么 | 一个数字编号，进程的"身份证号" | 你**自己进程**的句柄表里的一个引用 |
| 谁给的 | 系统创建进程时分配 | 你调用 `OpenProcess` 换来的 |
| 能直接用吗 | **不能**。拿 PID 当句柄用一定失败 | 能，`ReadProcessMemory` 等 API 要的就是它 |
| 有效期 | 进程活着就一直有效 | 你不 `CloseHandle` 就一直占着；进程死了就失效 |
| 权限 | 无 | **由 `OpenProcess` 的第一个参数决定**，要什么权限就申请什么 |

`lab02d.c` 里我故意写了一段"陷阱演示"：把 PID 强转成 HANDLE 传给 `ReadProcessMemory`，
你会看到它失败。这不是 bug，是让你亲眼确认这两者的区别。

`OpenProcess` 的权限参数是**按需申请**的，这是个重要的工程习惯：

```c
// 只想看内存布局 -> 只要这一个，很多进程都能开成功
OpenProcess(PROCESS_QUERY_INFORMATION, FALSE, pid);

// 想读内存 -> 加上 VM_READ
OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, FALSE, pid);

// 想改内存 -> 再加 VM_WRITE + VM_OPERATION
OpenProcess(PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_VM_OPERATION, FALSE, pid);
```

申请的权限越多，被拒绝的概率越大。第 10 课我们会正经处理这件事。

### 实验 A · 装 System Informer，看懂一个进程的 Memory 页

**A1. 安装**

- **工具叫什么**：System Informer（原名 Process Hacker，官方续作，开源免费）
- **为什么需要**：任务管理器只给你几个汇总数字，看不到"地址空间内部长什么样"。
  本课要看的就是内部。它是目前最清楚的免费工具。
- **从哪下**：`https://systeminformer.sourceforge.io/` → Downloads
  （或 GitHub 仓库 `winsiderss/systeminformer` 的 Releases 页）
  下载 **bin zip**（绿色版，解压即用，不用安装）。
- **装什么**：解压到一个目录，里面就是 `System Informer.exe` 等文件。
  第一次启动它会问要不要装**内核驱动**——本课**不需要**，选跳过/否即可。
  想看系统进程的详细信息时再回来装。
- **本阶段只用它的这些功能**：进程列表、双击进程后的 **Threads / Modules / Memory** 三个页、

### 实验 C：两个进程的 `0x12340000`

```
实例 1: PID=12345, 地址 0x12340000, 值 1234   → 十六进制 D2 04 00 00
实例 2: PID=12351, 地址 0x12340000, 值 1240   → 十六进制 D8 04 00 00
```

**地址完全相同，内容不同，互不影响。** System Informer 里两个进程的 Memory 页
各自都有一行 `0x12340000`。这就是虚拟地址空间隔离最直白的证据。

> 如果 `VirtualAlloc` 失败（错误码 487 `ERROR_INVALID_ADDRESS`），说明 `0x12340000` 被占了。
> 把源码里的 `WANTED_ADDR` 改成 `0x12350000` 重编即可。
> **这个失败本身也很有教育意义**：它说明地址空间是有限资源，好位置会被先来的模块占掉。

### 实验 D：四个栈的地址

```
[主线程 ] TID=12340  main_local      的地址 = 0x0019FB74
[线程 1 ] TID=12356  local_on_stack  的地址 = 0x00B7FB74
[线程 2 ] TID=12360  local_on_stack  的地址 = 0x00BBFB74
[线程 3 ] TID=12364  local_on_stack  的地址 = 0x00BFFB74
[全局   ] g_shared_counter 的地址 = 0x00F5B020   ← 注意这个！
```

**四个栈在四个不同的区域，全局变量在 EXE 映像里（Type = Image，Protect = RW-）。**

注意最后一个：`g_shared_counter` 是全局变量，它住在 `.data` 段，
在 System Informer 里属于 **`0x00F5xxxx` 那个 Image 区域**，不是 Private。
这就是"共享数据"和"私有栈"在内存布局上的真实差别——
**4 个线程改的是同一个物理地址，而它们的局部变量各自在不同地址。**

每块栈旁边你会看到：
```
0x00B80000   1044480   Reserve   Private        ← 1MB 预留，还没配物理存储
0x00B7F000      4096   Commit    Private   ---+G ← GUARD 哨兵页
0x00B70000     61440   Commit    Private   RW-   ← 真正在用的栈
```
这个"Reserve + Guard + Commit"三件套，是线程栈的标准长相。看到它就认得出来。

### 实验 E：堆增长的数字

```
第  0 轮  已申请    0 MB | CommitCharge    380 KB | WorkingSet   1200 KB
第  1 轮  已申请   10 MB | CommitCharge  10620 KB | WorkingSet  11800 KB
第  5 轮  已申请   50 MB | CommitCharge  51200 KB | WorkingSet  52300 KB
第 10 轮  已申请  100 MB | CommitCharge 102400 KB | WorkingSet 103500 KB
         新区块 0x05A00000 : 区域大小 10240 KB, 类型 0x20000, 保护 0x04, 状态 0x1000
         (类型 0x20000=MEM_PRIVATE 私有, 状态 0x1000=MEM_COMMIT)
```

三个数字的关系（你的具体数值会不同）：

- **CommitCharge 比"已申请"多一点点**：因为除了这 100MB，还有 EXE、DLL、栈、CRT 的堆。
- **WorkingSet 通常 ≥ CommitCharge**：WorkingSet 包含了共享的 DLL 页面（那些页也算在你头上），
  而 CommitCharge（`PrivateUsage`）只算**私有提交**。
  → 这就是为什么任务管理器有好几个内存列，它们统计的根本不是同一个东西。
- **新区块是 10240 KB = 正好 10MB，Type = Private，Protect = 0x04 (RW-)**：
  `malloc` 大块内存时直接向系统 `VirtualAlloc`，所以区域大小干干净净正好 10MB。
  如果你 malloc 的是 100 字节，你就看不到独立区域了——它被塞进已有的堆区域里。

### 实验 F：模块基址

```
PID                       = 23456
EXE 实际加载基址 (hSelf)  = 0x00F50000
PE 文件里写的 ImageBase   = 0x00400000
AddressOfEntryPoint(RVA)  = 0x00001234
入口点的真实虚拟地址      = 0x00F51234   (= 基址 + RVA)
DllCharacteristics        = 0x0160  -> 有 IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE，支持 ASLR

★ 实际基址 != ImageBase：ASLR 生效了！系统把它挪了 0xB50000 字节。
  这就是为什么你在 PE 文件里算出来的地址，不能直接拿去用在运行中的进程上。

main 的真实地址           = 0x00F515A0
模块基址                  = 0x00F50000
main 的 RVA (偏移)        = 0x15A0
基址 + RVA 算回来         = 0x00F515A0   -> 一致 ✔

main 开头的 16 个字节（机器指令）：
  55 8B EC 83 EC C0 C7 45 FC 64 00 00 00 C7 45
```

**看最后那 16 个字节**：`C7 45 FC 64 00 00 00` —— 这就是第 1 课那条
`mov dword ptr [ebp-4], 64h`（把 100 写进 money）。
**你在文件里搜到的字节，和在活着的进程内存里读到的字节，一模一样。**
因为代码段是被"映射"进来的，不是被"改写"进来的。

模块列表大概长这样：

```
共 21 个模块
#    Base               Size       Path
---- ------------------ ---------- --------------------------------
0    0x0000000000F50000 0x0000B000 C:\lab\lab02d.exe   <== 这就是你的 EXE
1    0x0000000077A00000 0x0019E000 C:\Windows\SYSTEM32\ntdll.dll
2    0x0000000076C00000 0x00120000 C:\Windows\System32\kernel32.dll
3    0x0000000075D00000 0x0028E000 C:\Windows\System32\KERNELBASE.dll
4    0x0000000076A00000 0x000C0000 C:\Windows\System32\msvcrt.dll
...
```

20 行源码 → 21 个模块。**你的 EXE 排在第 0 位，基址最小。**
系统 DLL 挤在 `0x75xxxxxx ~ 0x77xxxxxx`（32 位进程的顶端）。

### 实验 G：地址空间列表

```
BaseAddress        Size       State          Type             Protect
------------------ ---------- -------------- ---------------- -------
0x0000000000010000 4096       Commit  已提交 Private 私有     RW-
0x0000000000190000 65536      Commit  已提交 Private 私有     RW-
0x00000000001A0000 983040     Reserve 仅预留 Private 私有
0x0000000000F50000 4096       Commit  已提交 Image   映像     R--
0x0000000000F51000 12288      Commit  已提交 Image   映像     R-X
0x0000000000F54000 8192       Commit  已提交 Image   映像     R--
0x0000000000F56000 4096       Commit  已提交 Image   映像     RW-
0x0000000077A00000 2097152    Commit  已提交 Image   映像     R-X
...
非空闲区域共 87 个
已提交 Commit  合计       3840 KB  (其中 EXE/DLL 映像 3200 KB)
仅预留 Reserve 合计       2048 KB
```

**看点**：
- 你的 EXE（`0x00F5xxxx`）被拆成了 **4 行**：R-- / R-X / R-- / RW-。这就是"节按保护属性分块"。
- `Reserve` 那行**没有 Protect**（因为还不能访问，保护属性没意义）。
- 系统 DLL 的 `R-X` 区域加起来占了 Commit 的绝大部分——但那都是**共享**的，不是你独占的。

查系统进程失败时：

```
目标 PID = 892（别的进程）

!! OpenProcess 失败，错误码 5

   错误码 5 = ERROR_ACCESS_DENIED 拒绝访问。
   原因：目标进程的权限比你高（系统进程 / 管理员启动的进程），
         或者它受 PPL（受保护进程）保护。
   怎么办：用【以管理员身份运行】打开 cmd，再跑一次这个程序。
   要记住的是：这个拒绝不是游戏做的，是 Windows 内核做的。
```

管理员身份重跑后，大部分系统进程就能列出来了。
但像 `csrss.exe`、某些反作弊进程、开了 PPL 的进程，**管理员也照样被拒**——
那时错误码还是 5。这个天花板你要知道在哪，第 5 课开始碰游戏时会用到。

| `lab02e 某PID` 报错误码 5，但你确定那是普通程序 | 那个程序是**以管理员身份**启动的，而你的 cmd 不是。权限是"高看低可以，低看高不行" |
| `lab02e` 输出的区域数量和 System Informer 差很多 | 我的程序**跳过了 Free 区域**（不然几万行没法看）。System Informer 默认也不显示 Free。如果还是差，检查你是不是在看不同的进程 |
| `Commit` 数字对不上任务管理器 | 任务管理器有好几个内存列，统计口径不同。以 `Private Bytes` / "提交大小" 为准，它对应 `PrivateUsage` |

1. 确认你在 **x86** Native Tools 提示符里（标题栏会写 `x86`）
2. `dir *.exe` 看程序真的编出来了吗，时间是刚刚吗
3. 把**完整输出**（不是截图的一角）贴给我

## 【实验后思考题】

1. 实验 C 里两个进程都用上了 `0x12340000`。如果我在实例 1 里把那个值改成 999，
   实例 2 会看到吗？**如果我非要让它看到，Windows 提供了什么正规手段？**
   （提示：想想"共享内存"这个词，以及 Type = `Mapped` 的区域）

2. 实验 D 里 4 个线程的栈地址都不同，但全局变量地址只有一个。
   那么——**如果游戏里有 1000 个单位，每个单位都有"生命值"，
   这 1000 个生命值更可能存在"各自独立的区域"还是"同一块连续区域"？** 说理由。

3. 实验 E 里 malloc 10MB 出现了一个正好 10MB 的独立区域，
   那 malloc **100 字节**会出现新区域吗？如果没有，那 100 字节去哪了？
   （提示：这就是"堆管理器"存在的意义）

4. 32 位进程只有 2GB 用户地址空间。《英雄连》要装下 EXE + 几十个 DLL + 地图 + 几百个单位
   + 贴图 + AI 状态。**你觉得它有可能爆掉这 2GB 吗？** 爆掉会发生什么？
   （提示：`/LARGEADDRESSAWARE`，以及游戏崩溃时那个"内存不足"提示）

5. 实验 F 里 `基址 + RVA = 真实地址`。**那么"RVA"这个东西，为什么在逆向里比"真实地址"更有用？**
   （提示：想想 ASLR，想想你在网上查到的攻略地址）

6. 实验 G 里，普通权限读不了系统进程，管理员权限可以。
   **这个检查是谁在做？游戏能不能自己再加一层检查？**
   （提示：能，而且商业游戏和反作弊正是这么干的。想想那会是什么形态）

7. `kernel32.dll` 在你的进程里基址是 `0x76C00000`，在记事本里也是 `0x76C00000`。
   **为什么两个不同进程里同一个 DLL 的基址会一样？这是必须的吗？**
   （提示：想想 `.reloc` 节，想想如果每次都不一样会带来什么代价）

8. （承上启下）实验 F 里，`main` 的机器指令字节在**文件里**和在**内存里**是完全一样的。
   那 `g_shared_counter` 的**值**呢？文件里存的是 0，运行时是几百万。
   **为什么代码可以一模一样地映射，数据的值却可以完全不同？**
   （提示：`Commit` 的 `RW-` 页 和 `Image` 的 `R-X` 页，写权限不一样）
